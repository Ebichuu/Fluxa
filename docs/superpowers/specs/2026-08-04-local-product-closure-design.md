# Fluxa 本地产品闭环收口设计

日期：2026-08-04

状态：方案 A 已确认，待规格复核后实施

## 1. 目标与边界

本波次只处理 Fluxa 内可以独立闭环的四项产品问题：

1. 日历月快照改为持久后台缓存，页面请求只读取缓存。
2. 对账 `conflict` / `remote_missing` 进入独立的“对账待处理”，不混入媒体下载、入库的 `action_required`。
3. RSS 资源中心明确“追更待识别”，并为失效/重叠匹配提供可审计的归档清理闭环。
4. 发现页和共用海报组件识别缺图、加载失败和明确的白色无效图，使用带标题信息的稳定占位，避免反复请求同一失效地址。

本波次不做以下工作：

- 不接入 Symedia 剩余六项能力，不从文件路径、Emby 或归档结果推断 STRM、监听器或调度器成功。
- 不接入 Torra 订阅级 RSS/自动搜索模式推断，不修改 Torra 或 Symedia 配置。
- 不触发 Torra 搜索、追更推送、下载、qB、秒传、Symedia 或 Emby 写动作。
- 不删除 RSS 原始条目，不迁移任务身份，不改变现有媒体 `action_required` 统计语义。
- 不提交或读取 `services/nasemby-core/mcc_data.db`。

## 2. 方案选择

### 方案 A：本地闭环与外部证据分波次（选定）

先完成持久缓存、独立对账入口、RSS 失效匹配归档和海报兜底；把 Symedia/Torra 能力作为后续只读证据波次。优点是每项都能用本地 SQLite、现有快照和明确的前端状态完成验收，不会因为上游没有正式接口而扩大推断范围。

### 方案 B：一次性同时接入所有外部能力

日历、对账、RSS、海报和 Symedia/Torra 证据在同一波次发布。该方案会把缓存性能、匹配所有权和上游接口不确定性绑定在一个回滚点，失败时难以判断是 Fluxa 逻辑还是外部证据缺失，不采用。

### 方案 C：只改前端文案和筛选

只把“待识别”改名、增加前端筛选和海报占位，不改日历采集和 RSS 匹配台账。该方案无法解决首开 20 秒、对账数字漏出和失效候选持续占据评分列表，不采用。

## 3. 日历持久后台缓存

### 3.1 缓存键与记录

新增 `calendar_snapshot_cache` 日历快照持久表，规范键为：

```text
year + month + mediaType + includeUnlinked
```

每条记录至少保存：

- `scopeKey`：规范化后的键，不保存用户原始查询字符串；
- `payload`：已经完成去重、集级证据关联和日期统计的公开快照；
- `observedAt`、`freshUntil`、`lastSuccessAt`、`lastAttemptAt`；
- `confirmation`：`confirmed | partial | unknown`；
- `lastErrorCode`、脱敏 `lastErrorText`；
- `version`、`updatedAt`。

新增 `calendar_snapshot_refresh_queue` 刷新队列表。每个 `scopeKey` 最多一条当前队列记录，保存 `status=pending|running|succeeded|failed`、`requestedAt`、`lastRequestedAt`、`startedAt`、`finishedAt`、`leaseOwner`、`leaseUntil`、`attemptCount`、`idempotencyKey` 和脱敏失败信息。相同 scope 的重复请求只推进同一条队列记录，不创建并发构建。

历史事件中的 qB 完成、Symedia 归档、STRM 生成和 Emby 首次确认时间继续永久保留。缓存过期只影响当前快照确认程度，不删除历史事件。

### 3.2 读取和刷新

`GET /api/v2/calendar` 的 Fluxa 页面路径只读取 SQLite，不调用月份 loader、任务链全量快照、Torra 对账或历史事件全量索引。缓存状态分三类：

- 有效缓存：直接返回最后可靠摘要；
- 过期缓存：返回最后可靠 payload，标记 `partial` 并附带刷新状态；
- 无缓存：返回结构完整的 `200`、可空数值为 `null`、`confirmation=unknown`，不使用空数组冒充成功。

缺少或过期的动态月份由 `POST /api/v2/calendar/refresh-requests` 进入本地队列。请求只提交规范 scope 和幂等键，实际外部采集由后台 worker 完成；该 POST 返回 `202` 和当前队列状态，不等待刷新。`GET /api/v2/calendar` 始终纯读缓存，冷 scope 也不得由 GET 隐式写队列或现场重算；前端收到冷缓存/过期缓存后再显式提交刷新请求，并轮询同一个 GET。

后台刷新器使用进程锁加 SQLite 租约单飞：同一 scope 同时最多一个构建；容器多线程、重复定时和重复手动请求不得并发重算。外部读取发生在 SQLite 事务外，成功或失败使用短事务写入该 scope。

快照沿用现有 300 秒确认窗口；worker 每 30 秒领取一次到期队列项。刷新耗时不延长上一份快照的事实时间，只有新构建成功后才原子替换 `payload`、`observedAt` 和 `freshUntil`。

刷新失败时保留上一份完整 payload，返回“上次确认值 · 当前暂未确认”和脱敏原因；从未成功过才显示未知。后台 worker 不触发任何外部写动作。

### 3.3 scope 请求与预热

服务启动只把“Asia/Shanghai 当前月、`mediaType=all`、`includeUnlinked=false`”这一默认 scope 加入刷新队列，不自动预热上月、下月、其他媒体类型或未关联口径。用户打开其他 scope 时，前端先读取缓存；若缺失或过期，提交幂等的本地刷新请求并继续显示缓存/未知状态，随后轮询只读 GET。

每次合法刷新请求更新该 scope 的 `lastRequestedAt`。后台定时刷新当前月默认 scope，以及最近 30 天内请求过且已经过期的 scope；超过 30 天未使用的 scope 保留最后可靠快照，但不再自动续刷，直到用户再次提交刷新请求。日期边界统一按 Asia/Shanghai 计算，快照事实时间继续保存 UTC 原值。

刷新请求只允许合法年份、月份、媒体类型和 `includeUnlinked`，不携带外部 URL、凭据、路径或远端 ID。旧日历路由、查询参数、字段和状态码保持兼容。

### 3.4 验收

- 容器重启后日历首个 GET 不等待整月现场计算，目标在 500ms 内返回缓存或结构完整未知结果。
- 相同 scope 并发刷新只执行一次，后续请求复用同一结果。
- 上游采集失败不删除上一份可靠月快照。
- `includeUnlinked=false/true`、媒体类型和月份之间无缓存串扰。
- 单日详情只从对应月快照投影日期，不能带入整月计数。
- 等待缓存过期后，历史成功事件时间仍然存在。

## 4. 独立“对账待处理”

### 4.1 后端统计

在追更工作台和对账摘要中新增可选统计 `reconciliationActionRequired`，只统计：

- `reconciliationState=conflict`；
- `reconciliationState=remote_missing`。

`only_fluxa`、`only_torra`、未分类和临时未知不计入该数字。该统计按规范订阅键去重，不能按页面前 8 条或分页结果计算。

现有 `outcomeState=action_required`、`actionRequired`、任务链资源数和下载/入库异常保持原语义，不吸收对账异常。

### 4.2 筛选和界面

追更页新增独立入口“对账待处理 N 条”，固定使用可重复深链：

```text
/following?status=reconciliation_action_required
```

页面筛选同时匹配本地对账结果，不把对账问题伪装成媒体执行问题。每条记录保留原有“对账异常”原因和安全深链，首页仅作为辅助提醒，使用中性/待处理语义，不增加首页媒体异常总数。

筛选无结果、对账读取失败和远端暂不可读分别显示 `0`、`未知` 和独立原因，不相互替代。

### 4.3 验收

- 10 条 `conflict/remote_missing` 在追更页可通过独立入口全部找到。
- 下载、入库异常为 0 时，“需要处理”仍为 0，但“对账待处理”为 10。
- 首页辅助提醒可深链到该筛选，不改变 `actionRequiredResources`。
- 旧筛选、旧字段和旧状态码继续兼容。

## 5. RSS 表达与失效匹配清理

### 5.1 文案和统计

资源中心将用户可见的“待识别”改为“追更待识别”，明确它只统计“已关联追更且需要人工识别”的资源。全库未识别资源继续保留在中性未关联范围，不计入该待办。

### 5.2 重叠候选显示

同一作品季集或规范 artifact 出现多个订阅所有者时，候选组必须展示：

- 当前有效归属：订阅键、季集、规则状态和可评分状态；
- 失效归属：失联、订阅不存在、所有权冲突或身份不一致的原因；
- 是否允许进入评分主列表；
- 是否进入待整理列表；
- 当前候选是否可执行。

有效归属必须在展示和确认动作前重新读取当前 Fluxa/Torra 绑定、TMDB、媒体类型、季集和 artifact 唯一所有权。标题相似度不得用于恢复归属；无法唯一确认所有者时，整组保持待复核并禁止自动清理/下载。

### 5.3 归档清理闭环

清理流程固定为：

```text
预览 → 明确确认 → 重新核验 → SQLite 原子归档 → 审计留痕
```

预览返回规范匹配键、有效/失效归属、原因、影响数量和指纹；不返回下载地址、Cookie、Passkey、路径或远端原始 ID。指纹由排序后的匹配键、各匹配 `version`、归档状态、规范 owner key、身份版本、当前订阅绑定版本和清理规则版本生成，不包含标题或敏感原文。确认提交预览 ID、指纹、选中失效匹配和幂等键。

执行前任何所有权、身份、版本或状态漂移都使预览过期，整批回滚并要求重新预览。确认只更新失效匹配的归档状态/审计记录，不删除 `rss_items` 原始行，不删除候选证据，不触发 Torra 搜索、下载、qB、秒传、Symedia 或 Emby。

归档状态和操作记录必须可重复执行；第二次相同幂等键返回首次结果，不产生第二次归档。有效候选和所有权冲突候选不能被该入口误归档。

匹配记录新增 `archiveState=active|archived`、`archivedAt`、`archiveReasonCode`、`archiveRunId` 和 `version`；归档只改变失效匹配的可见性，不改变其身份、评分、候选证据或原始 RSS 行。新增 `rss_match_cleanup_runs` 与 `rss_match_cleanup_items`：运行表保存预览指纹、状态、数量、创建/确认时间和幂等结果，项目表保存规范匹配键、预览版本、原因和执行结果，不保存下载地址或上游敏感原文。

预览由 `POST /api/v2/rss-match-cleanups/previews` 创建并持久化为 `previewed`；确认由 `POST /api/v2/rss-match-cleanups` 提交预览 ID、指纹、选中项和幂等键。确认事务内先重验全部选中项，再统一更新匹配归档状态、写项目审计并把运行标记为 `applied`。任意一项漂移、冲突或写入失败时整批回滚；随后只用独立短事务将运行标记为 `stale` 或 `failed`，不得留下部分归档或伪成功项目。

### 5.4 验收

- 《直到T恤干透》E03/E04 的有效与失效归属在同一视图中可区分。
- 失效匹配可通过预览/确认归档，原始 RSS 条目数量不变。
- 所有权冲突或状态漂移时不产生部分归档。
- 归档后候选评分主列表不再展示失效匹配，待整理列表可查看审计记录。

## 6. 海报兜底

### 6.1 统一资源状态

共用 `PosterImage` 处理：

- 缺少 URL；
- 代理或原图加载失败；
- 明确无效图片（零尺寸、透明空图或近乎纯白的无内容占位）。

白色检测必须保守：图片成功加载后缩放到 16×24 采样画布，仅在同源代理可安全读取像素，且超过 99% 像素透明，或超过 99% 的非透明像素 RGB 各通道均不低于 250 且亮度标准差小于 2 时判定无效。`naturalWidth`/`naturalHeight` 为 0 直接判定无效；画布读取抛错或跨域像素不可读时保留正常图片，不凭猜测替换。

### 6.2 稳定占位和重试

占位卡保留标题首字符/短标题信息，不能只显示空白块或孤立图标。无效地址加入当前页面生命周期的失败集合，同一解析地址不重复发起请求；资源地址变化后才允许重新尝试。不能把外部失败地址写回业务台账。

### 6.3 验收

- 缺图、加载失败和白色无效图均显示有标题信息的占位。
- 同一失效 URL 在列表重渲染、筛选和展开过程中不循环请求。
- 正常浅色海报不因检测阈值被误替换。
- 发现页首屏不再出现白色空海报。

## 7. 外部证据独立波次

另开只读证据波次，暂不与本波次代码合并：

1. Symedia 剩余六项能力逐项寻找正式接口；只有独立结果 ID、媒体身份、季集范围、成功状态和时间齐全时才标记成功。
2. Torra 订阅级 RSS/自动搜索模式只读取正式订阅/调度证据；无法确认继续显示“暂未确认”。
3. 所有能力缺失、接口不完整、来源冲突或时间不可靠时保持 `unknown`，不从配置、标题、文件名、路径、Emby 或任务数量反推。
4. 该波次只新增可选只读字段、能力状态和诊断，不修改 Torra/Symedia，不触发搜索、下载、归档或订阅写入。

## 8. API 与数据兼容

- 现有日历、追更、RSS 路由和旧字段保留；新增缓存元数据、刷新状态、对账待处理统计和失效归档字段均为可选增量。
- `GET /api/v2/calendar` 只读 `calendar_snapshot_cache`；冷 scope 返回结构完整的 `200 + confirmation=unknown`。前端使用 `POST /api/v2/calendar/refresh-requests` 提交 `{year, month, mediaType, includeUnlinked, idempotencyKey}` 请求后台刷新，再轮询原 GET；GET 不写队列。
- `POST /api/v2/rss-match-cleanups/previews` 只生成持久预览，`POST /api/v2/rss-match-cleanups` 执行确认归档；两者不删除 `rss_items`，不调用外部服务。
- 所有新增 POST 具备幂等键；版本或指纹冲突返回结构化 `409`，参数错误返回 `400`，旧 GET 的状态码和字段类型不变。
- 公开错误使用固定脱敏文案，不暴露路径、URL 查询、Cookie、Passkey、Authorization、远端原始 ID 或上游错误原文。
- 失败刷新保留上一份可靠 payload；空缓存返回 `null/unknown`，不能返回虚假零值。

## 9. 测试与发布门禁

后端新增/扩展测试覆盖：日历缓存键、TTL、后台单飞、SQLite 原子写入、失败保留、冷启动空缓存、对账独立计数/筛选、重叠所有权预览与漂移回滚、清理幂等和公开脱敏。

前端新增/扩展测试覆盖：日历缓存加载状态、对账待处理深链、追更待识别文案、候选有效/失效归属展示、海报白图/失败占位和失败地址去重。

发布前必须通过：

```powershell
Set-Location services/nasemby-core
python -m unittest discover -s tests -t .
Set-Location ../..
npm run build
git diff --check
```

并完成 API 兼容、敏感信息扫描和缓存首开/并发实机验收。外部证据波次不作为本波次的通过条件。

## 10. 实施顺序

1. 日历持久缓存仓储、后台单飞刷新和纯读页面路径。
2. 对账待处理后端统计、筛选参数、追更入口和首页辅助提醒。
3. RSS 失效归属投影、预览/确认归档和审计留痕。
4. 统一海报失效检测、标题占位和失败地址去重。
5. 定向测试、全量回归、构建、契约/脱敏检查和实机验收。
6. 另立外部证据只读接入设计与实施波次。
