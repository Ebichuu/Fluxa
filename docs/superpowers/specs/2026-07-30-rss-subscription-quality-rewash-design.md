# Fluxa RSS 订阅绑定质量预筛与追更洗版总计划

日期：2026-07-30

状态：阶段 A-B 已完成实现，阶段 C-F 待实施

实施边界：只修改 Fluxa，不修改 Torra 源码

上位路线图：[Fluxa 可信媒体控制中心整体收口路线图](./2026-07-30-trustworthy-media-control-center-roadmap-design.md)

## 一、核心边界

### Torra 继续负责

- 创建和维护订阅；
- 首次缺集获取；
- 订阅分类与保存目录；
- 下载器选择；
- qB 标签；
- p115client 秒传链路；
- 用户配置的权重规则。

### Fluxa 负责补充

- 跨 RSS 批次保存候选；
- 将候选关联到具体 Torra 订阅和季集；
- 使用该订阅适用的 Torra 规则评分；
- 持续选出该集最高分版本；
- 发现更高分版本后，按照原订阅设置精准下发；
- 控制全站 PT 搜索频率。

Fluxa 不接管没有订阅归属的种子，也不自动负责首次缺集下载。

## 二、订阅绑定模型

每个可执行候选必须同时具备：

- Fluxa 订阅 ID；
- Torra 远端订阅 ID；
- TMDB ID；
- 媒体类型；
- 季号和明确集号范围；
- Torra 媒体分类；
- 适用权重规则 ID；
- Torra 下载器 ID；
- 保存目录和下载标签；
- RSS 来源及候选指纹。

自动执行前重新读取 Torra 订阅，确认：

- 订阅仍存在；
- Fluxa/Torra 映射没有变化；
- TMDB、媒体类型和季号仍一致；
- 分类和下载设置没有变化；
- 当前没有同集下载任务；
- 规则快照仍对应这条订阅。

前端不得提交或修改下载目录、规则 ID、下载器、分类和 RSS 下载地址，避免把候选错误下发到其他订阅。

## 三、目前项目还存在的问题

### P0：RSS 命中仍然触发全站分析

当前链路是：

`RSS 匹配 → submit_analysis(torra_subscription_id) → Torra 重新搜索 PT 站`

RSS 本身只充当触发信号，没有参与分析候选。这正是额外搜索仍然存在的原因。

改为：

`RSS 匹配 → 本地评分该 RSS 候选 → 必要时精准下发该候选`

### P0：候选只匹配“已经开始观察”的单元

当前 `rss_subscription_match_runtime` 只遍历活动中的 `quality_watch_units`。

如果高质量 RSS 在首版下载过程中到达，当时观察单元尚未建立，这条候选不会自动重新匹配。即使稍后首版入库，它也可能永远留在普通种子列表。

修复方式：

- RSS 入库时先完成作品和季集身份识别；
- 观察单元创建或基线确认后，反向扫描该作品最近的 RSS 候选；
- 使用首次下载时间作为候选下限，不只依赖 `baseline_ready_at`；
- 重复回扫保持幂等。

### P0：没有当前版本的可靠基线分数

当前观察单元保存了一些下载证据，但没有明确保存：

- 当前实际版本；
- 当前版本的 Torra 规则分数；
- 使用的规则版本；
- 评分字段来源。

没有基线分数就无法证明新 RSS 候选一定更好。

修复方式：

- 从 Torra 已下载文件名、任务链和 Symedia 成功文件中确定当前版本；
- 使用该订阅当前规则评分；
- 保存 `baselineArtifactKey / baselineScore / ruleHash`；
- 基线身份或版本信息不足时只展示候选，不自动洗版。

### P0：同一 RSS 范围可能产生多个执行动作

范围包可能同时匹配 E02、E03 多个观察单元。当前模型可能为多个单元建立匹配，后续容易重复触发。

修复方式：

- 一个 RSS 指纹只有一个 `artifactKey`；
- 一个 artifact 只有一个规范订阅所有者；
- E02–E03 可以投影到两个单元；
- 底层只能产生一次评分和一次下载动作；
- 任一集所有权冲突时整条候选禁止自动执行。

### P1：24/48 小时模型仍围绕定时搜索设计

现有设置中的检查时间点主要用于定时调用 Torra 全站分析，不适合 RSS 事件驱动。

调整为：

- 普通模式采用“跟随追更”；
- 新 RSS 到达即评分，不等检查时间；
- 观察单元在追更完成后进入宽限期；
- 24/48 小时只作为兼容的高级固定窗口；
- 普通 UI 移除“720、1440、2880 分钟检查点”。

### P1：RSS 清理可能删除仍有价值的候选证据

当前 `rss_items` 按 3/7/14 天清理。若匹配、评分和下载历史直接依赖原始 RSS 行，后续会失去审计依据。

调整为：

- 活动观察单元引用的 RSS 项目暂不删除；
- 已执行候选在 `provider_actions` 保存脱敏后的固定摘要；
- 下载地址和 Passkey 不复制到审计记录；
- 观察结束后才允许按保留策略清理原始项目。

### P1：规则适用范围必须按订阅计算

读取所有 Torra 规则还不够。Fluxa 还要复现 Torra 的规则选择过程：

- 订阅媒体分类；
- 规则生效分类；
- 规则启用状态；
- 版本控制条件；
- 优先级与覆盖策略。

如果同一订阅命中多条规则但优先级无法唯一确定，显示“适用规则未确认”，禁止自动下载。

### P1：Torra 自身自动搜索批次仍可能继续运行

即使 Fluxa 不再触发全站分析，Torra 中处于自动搜索模式的订阅仍会独立搜索。

控制室增加：

- RSS 模式订阅数量；
- 自动搜索模式订阅数量；
- 最近一次自动搜索批次；
- 本批实际搜索订阅数；
- 预计站点请求量。

提供“预览调整为 RSS 优先”，确认后才修改选中的 Torra 订阅模式。Fluxa 不能静默批量修改。

## 四、更新后的数据流

```text
PT RSS
  ↓
rss_items 原始台账
  ↓
身份与季集识别
  ↓
关联具体 Torra 订阅
  ↓
读取该订阅适用的 Torra 权重规则
  ↓
对指定 RSS 候选评分
  ↓
与该订阅、该集当前版本比较
  ├─ 低分/同分 → 正常保护
  ├─ 身份或规则不明 → 等待人工确认
  └─ 更高分 → 成为唯一最佳候选
                     ↓
              订阅级精准下发
                     ↓
          Torra 下载器 → qB → p115client
                     ↓
             115 → Symedia → Emby
```

## 五、精准下发设计

Fluxa 调用 Torra 现有下载器入口，但执行上下文必须从订阅派生。

请求 Fluxa 接口时，前端只传：

- `matchId`；
- `idempotencyKey`。

Fluxa 后端完成：

- 加载 RSS 匹配；
- 解析对应观察单元；
- 加载 Fluxa/Torra 订阅映射；
- 从 Torra 实时读取订阅；
- 解析下载器、分类、保存目录和标签；
- 验证候选分数严格高于基线；
- 调用 Torra 指定资源下发入口；
- 轮询 Torra 任务和 qB 结果；
- 记录订阅 ID、季集、候选指纹和 qB Hash；
- 等待 115、Symedia、Emby 后续证据。

这是一条“订阅级精准下载”，不是普通种子库下载按钮。

如果 Torra 通用下载器入口无法完整复用该订阅的分类、目录或插件上下文，则该候选只能人工预览，自动下发不得启用。

## 六、状态模型

### 观察单元

- `waiting_baseline`：等待首版和当前分数；
- `monitoring_rss`：持续监听后续版本；
- `upgrade_available`：发现更高分候选；
- `upgrade_submitting`：正在按订阅设置下发；
- `upgrade_downloading`：qB 已确认；
- `upgrade_processing`：等待秒传和入库；
- `upgrade_confirmed`：高分版本已成功入库；
- `protected`：只有低分、同分或规则拒绝；
- `blocked`：身份、规则或订阅绑定冲突；
- `closed`：追更结束且宽限期已过。

### 候选决策

- 当前最佳；
- 低于当前版本；
- 与当前版本同分；
- 被权重规则拒绝；
- 范围不兼容；
- 身份未确认；
- 规则未确认；
- 已精准下发；
- 已被更高分候选取代。

“当前最佳候选”与“当前已入库版本”必须分开，不能在下载尚未完成时提前更新基线。

## 九、实施顺序

### 阶段 A：订阅绑定与规则影子评分

状态：已完成实现，进入全量验证与独立提交。

- 建立稳定 Fluxa/Torra 订阅映射；
- 读取规则；
- 评分但不下载；
- 回扫首版下载期间进入的 RSS。

完成边界：自动 RSS 入口不再调用 Torra 整订阅分析；规则只通过正式只读接口读取。范围包共享一个产物和一次评分动作，所有权冲突整体阻断。缺少唯一规则、可靠身份、明确季集、候选大小或版本字段时保存“暂未确认”，不返回假零分。人工 Torra 分析接口保留为明确兜底，不属于自动影子评分。

### 阶段 B：候选冠军与基线

状态：已完成实现，进入全量验证与独立提交。

- 保存当前版本分数；
- 建立跨批次冠军；
- 解决范围包单一所有权；
- 种子库展示真实决策。

完成边界：当前版本只接受 Torra 明确季集文件，或具有可靠 TMDB、媒体类型、季集范围和成功状态的 Symedia 结果；qB 只能为精确同名产物补充大小，不能独立形成基线。多个不同当前版本、文件大小冲突或版本字段不足时维持“暂未确认”。同一观察单元的历史候选每次随新批次重新排名；范围包必须在覆盖的全部季集上同时获胜，否则整条产物退出冠军。种子库默认按订阅季集展示候选组、基线、最佳候选和脱敏评分明细。本阶段只写本地评分与冠军投影，不调用 Torra 搜索或下载，也不更新当前已入库基线为尚未完成的候选。

### 阶段 C：人工订阅级精准下载

状态：阶段 C0 只读预检已完成；真实精准下发受 Torra 正式能力缺口阻断。

- 前端只提交 `matchId`；
- 后端按订阅生成 Torra 下载参数；
- 验证 qB、p115client、115 和 Symedia 全链路；
- 失败不改变当前基线。

止损结论：Torra 正式洗版入口只接受 Torra 自身分析会话中的候选，通用下载器入口没有订阅 ID，且会绕过订阅级去重、分集文件选择、下载快照和已下载目标回写。Fluxa 不使用通用入口，不修改 Torra，也不把整订阅分析结果冒充 RSS 精准下载。阶段 C0 只提供空对象请求的只读预检，复核冠军、严格高分、订阅绑定、规则哈希、候选重评分、基线、qB 活动任务和 Torra 忙碌状态；结果固定追加 `TORRA_EXACT_RESOURCE_ENDPOINT_UNAVAILABLE`，不创建动作或执行下载。Torra 提供正式订阅绑定的指定 RSS 资源入口前，阶段 C 的真实下载和阶段 D 自动洗版保持关闭。

### 阶段 D：自动追更洗版

- 自动执行严格高分候选；
- 同分、冲突和规则过期全部阻止；
- 每个 artifact 只执行一次。

### 阶段 E：搜索降载

- 停止 Fluxa 定时触发 Torra 全站洗版；
- Torra 分析保留为人工兜底；
- 检测 Torra 自动搜索模式；
- 缺集兜底采用单订阅、全局并发 1 的队列。

### 阶段 F：实机验收

重点验证：

- 候选始终绑定正确订阅；
- 日漫候选不会使用国产剧目录或规则；
- 首版下载期间到达的高分 RSS 不会漏掉；
- E02–E03 范围包只下发一次；
- 一小时后出现高分版本仍能升级；
- 普通追更洗版不产生 PT 搜索；
- 秒传、Symedia 和 Emby 结果能回到同一订阅季集；
- RSS 清理后仍保留评分和操作审计；
- 下载地址、Cookie 和 Passkey 从未出现在公开响应与日志。

## 关键原则

Fluxa 不是对“某条种子”独立评分和下载，而是对“某条 Torra 订阅下的某一季集候选”持续评分，并严格复用该订阅的规则与下载链路。

## 实施记录

### 2026-07-30：阶段 C0 订阅级精准下载预检止损

**变更内容**：新增匹配级只读精准下载预检与种子库入口，实时复核候选、订阅、规则、基线和下载器状态，并固定返回 Torra 正式入口缺失的稳定阻断。

**变更理由**：Torra 通用下载器入口无法证明继承当前订阅的去重、分集文件选择和结果回写语义，不能作为订阅级精准下发实现。

**影响范围**：Fluxa RSS 匹配运行时、1 条增量 v2 API、React 种子库、机器契约和回归测试；不修改 Torra，不创建 provider action，不触发分析或下载，不公开下载地址、目录、远端 ID、Cookie 或 Passkey。

**决策依据**：正式订阅绑定资源入口缺失时必须止损，保留人工 Torra 整订阅分析作为独立兜底，但不能将其结果冒充 RSS 候选精准下载。

### 2026-07-30：阶段 B 可靠基线与跨批次冠军

**变更内容**：新增可靠当前版本解析、基线分数持久化、候选摘要、跨批次冠军重算、范围包完整覆盖约束和按季集候选组读取接口；种子库改为展示真实候选组。

**变更理由**：单次 RSS 评分无法证明候选优于当前已入库版本，也无法在后续批次到达时维持唯一冠军。

**影响范围**：Fluxa SQLite、RSS 匹配运行时、质量观察投影、`GET /api/v2/rss-matches?view=groups` 和种子库页面；不修改 Torra，不新增外部写动作。

**决策依据**：缺少可靠身份、版本、范围或唯一规则时宁可维持“暂未确认”；范围产物必须完整覆盖全部所有者后才可成为冠军。
