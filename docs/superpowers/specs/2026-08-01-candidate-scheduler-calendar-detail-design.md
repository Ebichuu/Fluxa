# Fluxa 候选来源调度与日历详情收口设计

日期：2026-08-01

状态：设计已确认，待实施

范围：只修改 Fluxa；不修改 Torra，不恢复 PT 搜索、追更推送、频道轮询或下载动作

## 1. 背景与结论

当前候选规则已启用，但候选来源的定时刷新依赖 `subscription-task` 总调度器。该线程除了运行本地候选刷新，还会运行订阅搜索轮询和频道模式轮询。直接开启 `MCC_SUBSCRIPTION_SCHEDULER_ENABLED` 会扩大外部动作范围，不符合 Fluxa 当前的安全边界。

日历月视图和周视图已能正常使用，但当日详情仍会重建月份来源并同步刷新整份任务链，实机耗时约 40～45 秒。资源中心的 `cleanup` 页内视图已存在，但应用级导航目标类型和 URL 解析器未登记该值。

本波次采用以下结论：

1. 新建只负责候选池刷新的独立调度器，现有 `subscription-task` 继续关闭。
2. 手动和定时刷新共用同一执行器、互斥锁、幂等写入和审计格式。
3. 日历日期详情优先从完整月快照投影，不再重复构建整月。
4. `cleanup` 成为可被全局导航系统完整序列化和恢复的资源视图。
5. 列表数量明确区分“当前范围”与“全库”。

## 2. 非目标与止损

- 不开启或修改 Torra 自动搜索、订阅推送、下载器选择、分类、保存目录或标签。
- 不调用订阅整体分析、PT 搜索、qB、p115client、Symedia 或 Emby 写接口。
- Torra 仍未提供订阅绑定的指定 RSS 资源入口时，精准下载继续在预检阶段阻断。
- Symedia 没有正式独立证据的六项能力继续显示“暂未确认”，不从归档、文件名、路径或 Emby 收录反推。
- 不重建日历事件台账，不改变日历去重、集级所有权和历史事件保留规则。

## 3. 独立候选来源调度器

### 3.1 组件边界

新增 `CandidateSourceScheduler` 运行时，只接受一个候选来源刷新回调。运行时不直接引用 Torra、qB、秒传、Symedia 或 Emby 客户端。

现有 `run_subscription_now()` 中的候选抓取、规范化、去重、`discover_candidates` 写入和过期处理收口为单一刷新函数。手动接口和定时循环都只能通过 `CandidateSourceScheduler.run()` 调用该函数。

调度线程使用独立名称 `candidate-source`、独立心跳和独立状态。它不调用以下任何函数：

- `run_due_subscription_search_poll()`
- `run_due_channel_mode_poll()`
- 质量观察搜索或缺集 PT 兜底
- Torra 追更推送或资源下发

### 3.2 权威状态

在订阅 SQLite 中新增单例调度状态。对外契约至少包含：

```text
enabled
lastRunAt
lastSuccessAt
nextRunAt
running
lastError
lastResult:
  succeededSources
  failedSources
  skippedItems
  addedCandidates
  updatedCandidates
observedAt
```

内部另保存：

- `scheduleKey`：当前已领取的 Asia/Shanghai 日期与执行时间键。
- `lastAttemptedScheduleKey`：防止重启反复补跑。
- `runId`：公开脱敏运行引用。
- `startedAt`、`finishedAt`、`version`：用于崩溃恢复与乐观并发校验。

设置中现有的候选规则、定时开关和执行时间仍是用户配置入口。调度状态保存运行时采用的配置投影，不建立第二套可编辑设置。旧 `douban.last_run_at`、`last_success_at` 和 `last_error` 只由新状态单向投影，禁止新旧两套逻辑同时写入。

全部时间在持久层使用 UTC；计算每日计划键和界面显示时转换为 Asia/Shanghai。

### 3.3 互斥、幂等与重启

手动和定时调用使用同一个进程互斥锁。执行前还必须在 SQLite 事务内领取运行槽位，以便将来运行时模式变化时仍能阻止重复执行。

领取成功后先持久化 `running=true`、`runId`、`startedAt` 和计划键，再访问外部候选来源。任何一个来源失败都不回滚其他来源已完成的本地候选写入。

运行正常结束时：

- 总是更新 `lastRunAt`、`running=false` 和结果计数。
- 只有全部已配置来源都成功时更新 `lastSuccessAt`。
- 任一来源失败时保存公开脱敏的 `lastError`，同时保留其他来源的成功数据。
- 列表中的候选写入继续使用现有稳定候选键，重复刷新只更新同一行。

重启时如果发现上次 `running=true`，先将其收口为“上次运行中断”并清除活动标记。已存在 `lastAttemptedScheduleKey` 的计划不再自动重试，防止每次重启都重复访问来源和写入候选。用户仍可以通过手动“更新来源”明确重试。

当今日计划已到期且未存在尝试键时，服务重启后最多补跑一次。在计划时间之后执行的成功手动刷新会满足当日计划，避免立即重复定时刷新；计划时间之前的手动刷新不消费当日计划。

### 3.4 状态语义

候选来源状态优先级为：

1. 定时开关未开：`disabled`，文案“候选自动更新未开启”，不计算逾期。
2. 正在运行：`running`，展示开始时间。
3. 最近运行有来源错误：`error`，展示成功、失败和跳过数量。
4. 已启用且当前时间超过 `nextRunAt + 2 小时`，但当期计划没有运行记录：`overdue`。
5. 已启用且尚无首次记录：`waiting_first_run`。
6. 最近一次完整成功且未逾期：`healthy`。

“候选自动更新正常”必须同时满足：候选规则启用、定时开关启用、调度运行时已启动、最近无错误、最近成功未逾期。

该能力仍是中性自动化状态。定时关闭或逾期不得改写媒体处理结果，也不得让首页的媒体结论变红。

### 3.5 审计与公开错误

手动与定时运行写入同一类审计记录，区别仅由 `trigger=manual|scheduled|startup_catchup` 表示。每次运行只保留一条汇总记录，具体来源失败放入可展开的脱敏摘要，不在活动列表逐条刷屏。

审计与公开响应禁止包含 URL 查询、Cookie、Passkey、Authorization、本地路径或未脱敏的上游错误原文。

## 4. 日历单日快速路径

### 4.1 快照键和读取流程

完整日历快照缓存键改为：

```text
year + month + mediaType + includeUnlinked
```

`view=summary` 继续构建一份完整月快照，再投影为轻量摘要。`view=detail&date=YYYY-MM-DD` 走专用路径：

1. 读取相同月份、媒体类型和未关联口径的完整快照。
2. 仅保留目标日期的条目。
3. 按当天条目重算 `entries`、`titles`、阶段计数和版本。
4. 不调用 `calendar_loader`、Torra 对账、`task_service.full_snapshot()` 或历史事件全量索引。

页面正常进入月视图或周视图时会先完成摘要请求。用户点击当天时，详情请求应直接命中该完整快照。

### 4.2 深链与并发

当用户直接打开包含日期详情的 URL 时，前端先发起对应月或周的摘要请求，该请求完成后再请求单日详情。这保证详情路径有可用的完整快照。

后端对相同缓存键的构建使用单飞锁。如果月摘要和详情请求因兼容消费者而同时到达，只允许一个完整月构建，其他请求复用结果，禁止并发访问全部 TMDB 季数据和任务历史。

无快照的兼容详情请求可触发一次受单飞锁保护的完整构建，但正常 Fluxa 界面不应进入此路径。这条兼容路径不放松事实契约，不用空值或推断结果换取速度。

### 4.3 缓存与历史事实

快照 TTL 继续为 300 秒。日历快照中的 qB 完成、Symedia 归档、STRM 生成和 Emby 首次确认可播放时间仍来自历史事件，不使用新鲜度删除。缓存到期只影响下次查询是否重建，不影响历史事件存续。

正常点击当日详情的响应目标为 2 秒左右。服务端记录脱敏的耗时、缓存命中与单飞等待信息，不记录条目标题、路径或远端 ID。

## 5. 资源中心导航和数量口径

### 5.1 `cleanup` 全局导航

`cleanup` 加入以下公共类型与逻辑：

- `TaskNavigationTarget.resourceView`
- `readNavigation()` 允许值
- `pathForNavigation()` 序列化
- 资源中心页内 URL 状态
- `popstate` 前进、后退和刷新恢复

`/rss-library?view=cleanup` 必须直接打开“待整理”，不先闪回“新资源”。未知 `view` 继续安全回退为 `new`。

### 5.2 当前范围与全库

五个工作视图标签继续显示服务端全库数：

```text
新资源  全库 4248
```

列表头部使用当前查询返回的 `total`，并明确显示时间范围：

- 默认 24 小时：`当前范围 549 条 · 最近 24 小时`
- 1 小时：`当前范围 N 条 · 最近 1 小时`
- 7 天：`当前范围 N 条 · 最近 7 天`
- 全部：`当前范围 4248 条`

如果另有搜索词、RSS 来源、身份状态或追更上下文，`total` 仍以服务端返回的所有当前筛选条件交集为准。不从当前分页长度推算。

## 6. API 兼容性

现有手动刷新路由保持不变，响应可选增加：

```text
trigger
runId
scheduler
sourceCounts
```

追更能力快照中的 `sourceScan` 保持可选增量，但它改为读取 `candidate-source` 权威状态，不再从 `subscription-task` 推断候选调度。

现有 HTTP 状态码、旧字段和路由保持兼容。并发刷新如未取得运行槽位，返回结构化的 `already_running` 结果和当前脱敏 `runId`，不启动第二次刷新。

日历路由、查询参数和响应结构保持不变；日期快速路径只修改服务端计算方式。

## 7. 错误处理

- 候选调度运行时失败不影响 RSS 私有源收集线程，不影响已有候选查询。
- 单个来源失败时继续执行其他来源，最终状态为部分失败，不伪称全部成功。
- 调度状态写入失败时不继续执行来源刷新，避免无法审计的重复运行。
- 日历快照构建失败时保留原有公开错误语义，不使用空数组冒充成功。
- 单日详情从快照投影时必须重算当天统计，禁止带入整月计数。
- `cleanup` 未知或已失效上下文保持只读，不因深链进入而触发候选分析或下载。

## 8. 验收

### 8.1 候选调度

- `candidate-source` 启用时，`subscription-task` 仍为关闭且不创建线程。
- 定时刷新只改变 `discover_candidates`、候选调度状态和审计；Torra、qB、秒传、Symedia 和 Emby 无新动作。
- 手动和定时同时到达时只有一个运行，另一个返回 `already_running`。
- 已逾期服务重启后最多补跑一次；再次重启不重复执行同一计划键。
- 运行中断后可手动重试，但不自动重复补跑。
- 一个来源成功、一个失败时，成功来源的候选已更新，结果汇总正确显示部分失败。
- 相同候选重复刷新不新增重复行。
- 关闭时显示“候选自动更新未开启”，不显示逾期。
- 开启后在宽限内不逾期；超过 `nextRunAt + 2 小时`且无当期运行记录时才逾期。
- 审计和公开错误不包含 URL 查询、Cookie、Passkey、凭据或路径。

### 8.2 日历

- 月摘要完成后点击当天，详情直接从同口径快照投影。
- 单日快速路径不调用月份 `calendar_loader`、Torra 对账或任务链 `full_snapshot()`。
- 普通当日详情在 fnOS 目标响应时间约 2 秒。
- 相同月份并发摘要和详情请求只构建一次完整快照。
- `includeUnlinked=false` 和 `includeUnlinked=true` 使用独立缓存键，计数不串扰。
- 单日统计只包含目标日期，不带入整月数字。
- 等待 300 秒后历史归档和首次确认可播放时间仍存在。

### 8.3 资源中心

- `/rss-library?view=cleanup` 直接打开待整理视图。
- 刷新、前进和后退后仍保持 `cleanup`。
- `pathForNavigation()` 可生成 `view=cleanup`，`readNavigation()` 可还原。
- 默认列表显示“当前范围 N 条 · 最近 24 小时”。
- 切换“全部”后显示“当前范围 N 条”。
- 视图标签继续显示“全库 N”，列表数与标签数不再被误解为同一口径。

### 8.4 回归与发布前检查

- 后端定向测试覆盖调度、并发、重启、部分失败、日历快照投影和并发单飞。
- 前端类型检查、生产构建和导航单元测试通过。
- 公开 API 契约保持只增字段、旧路由和旧状态码兼容，并通过脱敏检查。
- 实机确认候选池更新时 Torra 搜索数、推送数和 qB 活跃数没有因本次操作增加。
- 精准下载和 Symedia 未接入能力保持现有阻断与“暂未确认”语义。

## 9. 实施顺序

1. 新增候选调度状态和仓储接口，不改调度行为。
2. 抽出候选刷新执行器，先将手动“更新来源”切换到新执行器。
3. 新增独立 `candidate-source` 循环、计划键、补跑和能力状态投影。
4. 新增日历单日快照投影、缓存口径键和单飞构建。
5. 收口前端日历深链请求时序、`cleanup` 全局导航和当前范围文案。
6. 运行定向回归、全量回归、构建、API 兼容和脱敏检查，再进行 fnOS 安全实机验收。
